## 前提

- このアプリは「手入力中心の家計簿」から、「候補確認中心の家計簿」へ移行する
- 正式な帳簿データは 1 件ずつ保持する
- 銀行 API の本格自動連携は前提にしない
- メール / VPN / OCR / 手動入力を候補として集約する
- AI は補助役であり、自動で正式記帳を確定してはいけない

## 今回の実装方針

- `ui.md` の情報設計と優先順位に従うこと
- `IMPLEMENTATION_SPEC_2026-03-21.md` の DB / API / UI / メール受信方針に従うこと
- 既存の `DailyRecord` / `AccountTransfer` を正式記録の正として扱うこと
- 候補と正式記録を混在させないこと
- 実装対象に対して、必要最小限で一貫した変更にまとめること

## 作業ルール

1. まず現状コードを確認し、今回の変更範囲を明確にしてください
2. 変更前に、どのファイルをどう変えるか短く整理してください
3. 仕様に不足がある場合は、次の優先順位で判断してください
   - `IMPLEMENTATION_SPEC_2026-03-21.md`
   - `ui.md`
   - 既存コードとの整合性
4. 既存の unrelated な変更は巻き戻さないでください
5. 実装後は、変更内容と残課題を簡潔にまとめてください

## 実装時の優先順位

優先順は以下です。

1. 候補キュー関連の基盤
2. 候補インボックス UI
3. 候補確認フロー
4. クイック記録シート
5. ホーム再設計
6. メール受信基盤 MVP
7. VPN イベント統合

## 重要な禁止事項

- AI の推測だけで金額を確定しない
- 候補を自動で正式記帳しない
- `ui.md` にない従来中心の画面構成へ戻さない
- 「とりあえずフォームを増やす」方向で解決しない

## 期待する出力

- 必要なコード変更
- 必要なら migration / schema 更新
- 必要なら新規 API / UI コンポーネント追加
- 最後に:
  - 何を実装したか
  - 何をまだ実装していないか
  - 次に進むなら何をやるべきか

## 補足

このプロジェクトで最も重要なのは、
「アプリを開いて思い出して全部入力する」のではなく、
「候補が溜まっていて、開いたら 1 件ずつ確定できる」状態を作ることです。
