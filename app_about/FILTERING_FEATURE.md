# フィルタリング / ブロック基盤 導入アシスト

更新日: 2026-03-15

この文書は、`tamelog` に追加予定のフィルタリング / ブロック基盤について、
既存アプリのどこにどうつなぐかを分かりやすく整理したメモです。

今の `tamelog` は、すでに次の土台を持っている。

- 一般ユーザー向けページ
  - ホーム
  - 記録
  - 目標
  - 衝動買いチェック
  - 設定
- 管理者向けページ
  - 招待管理
  - 管理
- 既存 API
  - `/api/users/me/preferences`
  - `/api/admin/*`

そのため、新機能は完全に別アプリとして作るのではなく、
`tamelog` を「設定 UI / 分析 UI」として使い、
VPN / Proxy 側を「実行エンジン」として連携させるのが自然。

## 1. この機能でやりたいこと

- ユーザーごとに通信制御ルールを持つ
- EC サイトや決済系サービスへのアクセスを、時間帯ごとに制限する
- ブロック時は警告を出す
- 通信履歴を管理者側で確認し、時間帯別の傾向を分析できるようにする

重要な前提:

- ユーザーには具体的なドメイン一覧を見せない
- ユーザーには `ECサイト`、`決済アプリ` のようなカテゴリで設定させる
- 実ドメイン管理は管理者のみが行う

## 2. 機能の全体像

役割は次の 2 つに分かれる。

### 2.1 `tamelog` 側

- ユーザー管理
- ブロックカテゴリ設定
- 時間帯設定
- 管理者向けドメイン管理
- アクセスログ閲覧
- 時間帯別分析
- 通知設定

### 2.2 ネットワーク制御側

- WireGuard で通信をサーバー経由にする
- mitmproxy でアクセス先を判定する
- ブロック対象なら遮断する
- ログを保存する
- `tamelog` が定義したルールを読み込む

要するに、`tamelog` は設定 UI と分析 UI を担当し、
実際に止める処理は VPN / Proxy 側が担当する。

## 3. 既存アプリのどこに入れるか

この機能は、今あるページに次のように差し込む。

### 3.1 一般ユーザー: `設定` ページ

今の `設定` ページには、すでに次の要素がある。

- プロフィール
- 通知設定
- カテゴリ管理

ここに新しく追加するのは、
`ブロック設定` セクションである。

追加イメージ:

- ECサイトブロック時間帯
- 決済アプリブロック時間帯
- Web Push を受け取るか
- VPN 接続ガイド
- CA証明書導入状況

つまり、ユーザーは `設定` 画面だけで
「いつ、何系を止めたいか」を決める。

### 3.2 管理者: `管理` ページ

今の `管理` ページには、すでに次の責務がある。

- ユーザー一覧
- ユーザー停止 / 再開
- OpenAI API キー管理
- システム状態表示

ここに新しく追加するのは、次の管理機能である。

- サービスカテゴリ管理
  - `EC`
  - `PAYMENT`
- カテゴリに属するドメイン一覧管理
- ユーザーごとの VPN IP 状態確認
- アクセスログ閲覧
- 時間帯別アクセス分析

つまり、管理者は既存の `管理` ページを拡張するだけでよい。

### 3.3 一般ユーザー: `衝動買いチェック` との関係

今の `衝動買いチェック` は、
「欲しいものを 24 時間保留する」機能である。

新機能はこの思想とかなり相性が良い。

つなぎ方の例:

- `衝動買いしやすい時間帯` をブロック時間帯の初期値に使う
- ECカテゴリへのブロック回数を、衝動買い抑制の指標として使う
- 保留リスト登録後、一定時間だけ ECカテゴリを強めに制限する

つまり、新機能は別物ではなく、
既存の `衝動買い防止` をネットワーク側まで広げたものとして扱える。

## 4. 実際の連携の流れ

連携の流れはシンプルにすると次の通り。

1. ユーザーが `設定` 画面でブロック時間帯を保存する
2. `tamelog` が DB にスケジュールを保存する
3. `tamelog` が Proxy 用のルールファイルを出力する
4. mitmproxy がそのルールを読み込む
5. VPN 経由の通信が来たら、送信元 IP からユーザーを特定する
6. URL の属するカテゴリを判定する
7. その時間帯がブロック対象ならブロックページを返す
8. 同時にログを保存する
9. `tamelog` がそのログを管理画面や分析画面に出す

重要なのは、
`tamelog が通信を直接止めるわけではない`
という点である。

役割分担はこうなる。

- `tamelog`
  - 設定を作る
  - ルールを保存する
  - ログを見る
  - 分析を見せる
- WireGuard / mitmproxy
  - 通信を受ける
  - 判定する
  - 実際に止める
  - ログを書く

## 5. 既存 API にどう足すか

今のアプリには、すでに
`ユーザー設定 API` と `管理者 API` がある。

そのため、増やし方も分かりやすい。

### 5.1 ユーザー側 API

既存:

- `GET /api/users/me/preferences`
- `PUT /api/users/me/preferences`

追加候補:

- `GET /api/users/me/block-settings`
- `PUT /api/users/me/block-settings`
- `GET /api/users/me/push-status`
- `POST /api/users/me/push-subscriptions`

考え方:

- 今の `preferences` は通知中心
- 新機能は意味が大きいので、別 endpoint に分けた方がよい

### 5.2 管理者側 API

既存:

- `GET /api/admin/users`
- `POST /api/admin/users/:id/suspend`
- `GET /api/admin/config`
- `PUT /api/admin/config`
- `GET /api/admin/system-info`

追加候補:

- `GET /api/admin/service-categories`
- `POST /api/admin/service-domains`
- `PUT /api/admin/service-domains/:id`
- `DELETE /api/admin/service-domains/:id`
- `GET /api/admin/access-logs`
- `GET /api/admin/access-analysis`
- `GET /api/admin/vpn-clients`

考え方:

- 既存の `adminRoutes` に追加していくのが自然
- 一般ユーザーには見せない情報なので、管理者専用ルートでまとめる

## 6. DB はどうつなぐか

今の DB は `User`、`SystemConfig`、`ImpulseItem`、`UserPreference` などを持っている。
ここに次を足すとつながりやすい。

### 6.1 ユーザーと VPN の対応

- `VpnClient`
  - `userId`
  - `vpnIp`
  - `publicKey`
  - `status`

これで、
`10.66.66.2 は誰の通信か`
をアプリ側でも分かるようにする。

### 6.2 管理者が持つカテゴリとドメイン

- `ServiceCategory`
  - `code`
  - `name`
- `ServiceDomain`
  - `categoryId`
  - `domain`
  - `enabled`

ここで、
`amazon.co.jp は EC`
`paypal.com は PAYMENT`
という対応を管理する。

### 6.3 ユーザーが持つ時間帯設定

- `UserBlockSchedule`
  - `userId`
  - `categoryId`
  - `dayOfWeek`
  - `startTime`
  - `endTime`
  - `enabled`

これが、設定画面で保存する本体になる。

### 6.4 Proxy から入るログ

- `AccessLog`
  - `userId`
  - `vpnIp`
  - `host`
  - `url`
  - `categoryId`
  - `blocked`
  - `reason`
  - `timestamp`

このログはユーザーには直接見せず、
管理者画面と分析用に使う。

## 7. ユーザーに見せる設定

ユーザー画面では、具体的なドメインは出さない。
出すのはカテゴリと時間帯だけにする。

例:

- ECサイトを 22:00 - 08:00 はブロック
- 決済アプリを 00:00 - 23:59 は常時ブロック

この形にすると、UI が分かりやすくなり、
管理者だけが対象サービス一覧を保守すればよくなる。

## 8. 管理者だけが持つ設定

管理者画面では、カテゴリに属する実ドメインを管理する。

例:

- `EC`
  - `amazon.co.jp`
  - `amazon.com`
  - `rakuten.co.jp`
- `PAYMENT`
  - `paypay.ne.jp`
  - `paypal.com`
  - `stripe.com`

注意:

- `決済アプリ` という見せ方はできるが、実際には Web ドメインや API 通信先で判定する
- ネイティブアプリ通信は、想像より複数ドメインに分かれることがある

## 9. ログと通知の考え方

### 5.1 ログ

アクセス履歴は管理者側だけに保存する。

保存候補:

- timestamp
- userId
- vpnIp
- host
- url
- category
- blocked
- reason

ユーザーには生 URL 一覧を見せない方が設計として安定する。

### 5.2 通知

ユーザーには、対象カテゴリへのアクセス時に警告を出す。

候補:

- Web Push
- アプリ内通知
- ブロックページ表示

注意:

- Web Push は端末やブラウザ制約がある
- iPhone では動作要件が厳しめ
- 最低限の通知としては、まずブロックページ表示を優先した方が確実

## 10. 時間帯分析

ログを蓄積すると、次のような分析が可能になる。

- ECカテゴリへのアクセスが多い時間帯
- 決済カテゴリへのアクセス頻度
- ブロックされた回数の推移
- 平日 / 休日の差分

管理者向けだけでなく、将来的にはユーザー向けに
「夜に衝動買いが増えやすい」といった気づきを返す材料にもなる。

## 11. 実装のすすめ方

いきなり全部やらず、次の順で入れるのが安全。

### Step 1

- Prisma モデル追加
- 管理者用ドメイン管理
- ユーザー用時間帯設定
- 設定画面 / 管理画面の UI 追加

### Step 2

- VPN IP とユーザーの紐付け
- `rules.json` の出力
- mitmproxy でカテゴリ判定
- ブロック処理

### Step 3

- アクセスログ保存
- 管理者向けログ画面
- 時間帯分析
- ダッシュボード用集計

### Step 4

- Web Push
- 通知最適化
- 衝動買いチェックとの連動

## 12. ルールファイル連携のイメージ

最初の連携は、DB 直結より
`JSON ファイル受け渡し` の方が分かりやすい。

流れ:

- `tamelog` が DB から有効ルールを読む
- `/opt/mitm-filter/rules.json` を生成する
- mitmproxy が数秒ごとに再読込する

例:

```json
{
  "users": [
    {
      "userId": "user_1",
      "vpnIp": "10.66.66.2",
      "schedules": [
        {
          "category": "EC",
          "days": [1, 2, 3, 4, 5, 6, 0],
          "start": "22:00",
          "end": "08:00",
          "enabled": true
        }
      ]
    }
  ],
  "domains": {
    "EC": ["amazon.co.jp", "amazon.com", "rakuten.co.jp"],
    "PAYMENT": ["paypal.com", "paypay.ne.jp"]
  }
}
```

この方式なら、
アプリと Proxy の責務境界が分かりやすい。

## 13. 実装上の注意

- `家計アプリ本体` と `VPN / MITM 基盤` は責務が違う
- 同一サーバー上でも、少なくとも別プロセス / 別設定として扱う
- HTTPS の制御には CA 証明書配布が必要
- 証明書ピンニングのあるサービスは制御できないことがある
- ブロックページへの誘導より、proxy 自身がレスポンスを返す方が安定しやすい

## 14. この機能の設計判断

現時点では、次の方針が妥当。

- ユーザーにはカテゴリだけを見せる
- 実ドメインは管理者だけが管理する
- ログは管理者専用にする
- 通知はまずブロックページ優先、Web Push は後段
- 分析は時間帯別集計を主軸にする

## 15. 画面ごとの完成イメージ

### 一般ユーザー

- `設定`
  - ブロック時間帯を設定
  - 通知有無を設定
  - VPN / CA証明書の導入状況を確認
- `衝動買いチェック`
  - 行動抑制の文脈として連携

### 管理者

- `管理`
  - カテゴリごとの対象ドメインを管理
  - VPN クライアント状態を確認
  - アクセスログを見る
  - 時間帯分析を見る

### ネットワーク基盤

- WireGuard
  - ユーザー通信の入口
- mitmproxy
  - 判定とブロックの実行
- Nginx
  - ブロックページ配信
