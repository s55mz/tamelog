# 貯めログ 開発フロー

更新日: 2026-03-12

この文書は、日々の開発をどう進めるかを揃えるための運用フローです。
実装順は `develop/PLAN.md` を参照し、この文書では 1 機能ごとの進め方を定義します。

## 1. 基本フロー

1. 対象機能を決める
2. 関連仕様を確認する
3. 影響する DB / API / 画面を洗い出す
4. 先に業務ルールを固定する
5. DB から実装する
6. API を実装する
7. 画面を実装する
8. テストと手動確認を行う
9. 文書との差分を解消する

## 2. 着手前チェック

作業前に必ず確認する。

- 画面仕様は `app_about/frame.md`
- API / DB 要件は `app_about/REQUIREMENTS.md`
- 未解決事項は `app_about/CONCERNS.md`
- 配備や起動条件は `app_about/DEPLOYMENT.md`

確認結果として明らかにするもの:

- 対象画面
- 対象 API
- 対象テーブル
- 権限要件
- 失敗時の UI

## 3. 1 機能の実装順

### 3.1 仕様確認

- 対象画面の役割を確認する
- 必須入力と任意入力を分ける
- 正常系と失敗系を確認する
- MVP 範囲か次段階かを確認する

### 3.2 データ設計

- Prisma schema に必要なモデルと制約を定義する
- enum を先に揃える
- `userId` 境界を確認する
- トランザクションが必要な処理を決める

### 3.3 API 設計と実装

- リクエスト / レスポンス形式を仕様に合わせる
- バリデーションを実装する
- エラーメッセージを日本語で短くする
- 認証 / ロール制御を入れる

### 3.4 UI 実装

- 先に導線を通す
- 次に見た目と入力補助を整える
- Dialog、Sheet、Toast の共通パターンを守る
- モバイルと PC のナビ差分を確認する

### 3.5 確認

- API 単体で動くか
- 画面から最後まで通るか
- 文書と用語が一致しているか

## 4. レイヤー別の実装原則

### DB

- 金額は円単位の `Int`
- 残高は `Account.balance` に保持
- 目標進捗は `GoalRecord` 集計
- 削除制約はアプリ側でも守る

### API

- 形式は JSON
- エラーは `{"error":"..."}` を基本とする
- ID 指定時は必ず `userId` で絞る
- 管理者 API は認証とロール確認を必須にする

### UI

- 短文中心
- 数字は見やすく大きく
- 空状態の説明は短くやさしく
- 保存成功は短いトースト
- 否定感の強い文言を避ける

## 5. 優先すべき実装単位

日々のタスクは、できるだけ以下の粒度に分ける。

- 1 API 群
- 1 画面
- 1 テーブル周辺
- 1 業務ルール

例:

- セットアップ API 一式
- 認証画面一式
- 口座 CRUD
- 記録編集時の残高再計算

## 6. 機能ごとの推奨順

### セットアップ / 認証

1. `SystemConfig`, `User`, `Invitation`
2. JWT と middleware
3. セットアップ API
4. ログイン、登録 API
5. セットアップ画面、ログイン画面、登録画面

### 初期設定

1. 給料日更新 API
2. デフォルトカテゴリ投入
3. 初期口座、初期目標 API
4. `UserSetupWizard`

### 記録 / 口座

1. `Account`
2. `DailyRecord`
3. `AccountTransfer`
4. 残高更新ロジック
5. 記録画面、口座画面、家計簿画面

### 目標 / ホーム / 進捗

1. `Goal`, `GoalRecord`
2. 進捗集計
3. 注目目標ロジック
4. 目標画面、ホーム、進捗画面

### 管理者

1. 招待 API
2. ユーザー管理 API
3. システム設定 API
4. 招待管理画面、管理者画面

## 7. レビューの流れ

1. 仕様どおりか確認する
2. 業務ロジックに破綻がないか確認する
3. 権限漏れがないか確認する
4. UI 文言が設計方針に合うか確認する
5. 次の機能に進める状態か確認する

## 8. 仕様変更時の流れ

1. まず `app_about/frame.md` または `app_about/REQUIREMENTS.md` を更新する
2. 未確定事項なら `app_about/CONCERNS.md` に追加する
3. その後にコードを修正する
4. 変更に合わせて `develop/PLAN.md` がズレたら更新する

## 9. ブロッカーが出たとき

- 仕様不明なら、まず文書の不足箇所を特定する
- 未確定事項なら `CONCERNS.md` へ分離する
- 実装依存が強いなら、先に下位レイヤーへ戻る
- AI や SMTP のような外部依存は、未設定時フォールバックを先に作る

## 10. Definition of Done

1 つの機能は、以下を満たしたら完了とみなす。

- DB / API / UI の必要範囲がつながっている
- 正常系が通る
- 主要な失敗系が通る
- 権限と `userId` 境界が守られている
- 文書と実装の用語が一致している
- 次の機能が着手できる状態になっている
